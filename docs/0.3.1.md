# THC 0.3.1: build spec

**Status:** ready to build. **0.3.0 has shipped** (NSFW portal, Screenshots tab, back up and restore, settings across releases, performance baseline, history and thumbnail fixes); the current version is 0.3.0. 0.3.1 is a patch release: a bug fix with a small replacement feature and two small polish items. No big new features. The big portal work (#27) is planned for 0.4.0 and builds on this release.

## How to work on this (read first)
- Work on `dev`; never push to `main`. Commit and push after each slice (see "Build order"), and run `git pull --rebase origin dev` before pushing (CI also pushes package builds to `dev`).
- **Deliver 0.3.1 efficiently.** Build what this file says.
- **If you find a bug, a missing piece, an idea, or anything out of scope: file a new GitHub issue and move on.** Do not stop to fix it, and do not widen a slice. Only fix it now if it blocks the slice you are on, and say so in the commit.
- Each fix gets a test that fails before the fix and passes after.
- Keep `README.md`, `CHANGELOG.md` and this file true as you go. If you deviate from this spec, write the deviation here and say why.
- The hard rules in `AGENTS.md` still apply (no network, never write to media files, C only, three operating systems, history compatibility, settings compatibility).

## Rules for every change
- Private and local: no network calls, no telemetry, no accounts.
- Never write to, move, or rename media files.
- Works on Windows, Linux (Wayland and X11) and macOS.
- Keyboard accessible, scalable text, high contrast.
- Logic that does not need SDL goes in `thc_core` and is tested there.
- Confirmation windows are real modal dialogs.
- Anything marked NSFW must never leak into the main portals, the system, caches or logs (see `docs/0.3.0.md`, section 6).

## 1. #34: an NSFW folder replaces the name rules

**Problem:** the NSFW folder-name rules (Settings → Privacy: "Treat folder names that match a rule as NSFW") do not work as expected. They are removed; the user chooses an **NSFW folder** instead, THC reads it, and the NSFW portal **sorts what it finds by subfolder**. Full context is in issue #34.

### Behavior
- **Settings → Privacy (or Library): "NSFW folder"**, with a folder picker like the other library folders (Choose, Change, Remove). One folder.
- THC **scans it** the same way as the video, music and audiobook folders (read-only, in the background). **Everything in it is NSFW.**
- **Grouping by subfolder in the NSFW portal:** a new **Folders** view (a fourth sub-tab next to Video, Music and Audiobooks, shown only when an NSFW folder is set). Each **direct subfolder** is a **group** (name and item count). Opening a group lists its items. Files directly in the NSFW folder go in a group named **"Unsorted"**. Deeper subfolders show as nested groups. Empty folders are hidden.
- The files in the NSFW folder also show in the NSFW portal's **Video, Music and Audiobooks** views by kind, so nothing is only reachable one way.
- Items marked NSFW from the normal library (right-click, **N**) stay supported and show in the NSFW portal as before (not in the Folders view, since they live elsewhere).
- **Never shown elsewhere:** content in the NSFW folder does not appear in Video, Music, Audiobooks, sections, search, Continue watching, Up next, counts or queue suggestions. If the NSFW folder lies **inside** another library folder, that folder's scan and views **exclude** it, so nothing appears twice.
- Lock, hide-tab, panic, masked titles, no history by default, and NSFW thumbnail and screenshot folders all apply to these items like any NSFW item.
- THC never writes to, moves or renames anything in the NSFW folder.

### Removing the rules safely
- Remove the rules UI and the matching code (`nsfw_rules_match` and its use in `nsfw_hidden()`), and every mention of NSFW name rules in `README.md` and `docs/0.3.0.md`.
- **Do not delete the settings keys.** Per the settings compatibility rule, `nsfw_rules_enabled` and `nsfw_rules` are still accepted and written back unchanged (unused).
- Folders that were NSFW only because of a rule stop being NSFW. If old rules are present at start, show a **one-time notice** in Settings: "NSFW name rules were removed. Choose an NSFW folder or mark items instead", with a button to the setting. Nothing is deleted. Explicit tags and "Not NSFW" overrides are unaffected.

### Settings
| Key | Type | Default |
| --- | --- | --- |
| `nsfw_dir` | path | empty (none) |
| `nsfw_rules_enabled`, `nsfw_rules` | kept, unused | unchanged |

`nsfw_roots` ("treat this library folder as NSFW") stays. Add `nsfw_dir` to back up and restore like the other folder settings. `thc-inspect` reports whether an NSFW folder is set, never its contents or file names.

### Data
A new library root for the NSFW folder (the root list and the `nsfw_roots` bit mask index roots, so check every place that sizes arrays by the number of roots). No database schema change is expected; if one is needed, follow the history compatibility rule.

### Files
`src/nsfw.c`, `include/nsfw.h` (remove the rule matching), `src/nsfw_app.c`, `include/settings.h`, `src/settings.c`, `src/screen_settings.c` (folder row, notice), `src/scan.c` and `src/app.h` (the new root), `src/library.c` and the portal files (exclusion), `src/portal_nsfw.c` (Folders view), `src/backup.c`, `tools/inspect/`, `README.md`, `docs/0.3.0.md`, tests.

### Tests
- Choosing the folder makes its items NSFW; removing it makes them normal again.
- Grouping: direct subfolders become groups, loose files go to "Unsorted", nested folders, empty folders hidden, unicode and long names.
- Nothing from the NSFW folder appears in Video, Music, Audiobooks, sections, search, Continue watching, Up next or counts; a NSFW folder inside another library folder is excluded there and appears once.
- Old `nsfw_rules` keys are preserved unchanged on save, have no effect, and trigger the one-time notice.
- Explicit tags and overrides still work; lock, hide-tab and panic apply to these items; no history is recorded by default.
- Back up and restore include `nsfw_dir`; `thc-inspect` reports the folder without file names.
- No media file or folder is modified; no network.

## 2. #28: show why an item is NSFW

**Problem:** `nsfw_hidden()` already returns a reason (`NSFW_WHY_*`), but the NSFW portal does not show it.

**Fix:**
- A small **text line** (not only an icon or color) on each row and card in the NSFW portal: **"Marked", "In a NSFW folder", "In a folder you marked", "Library folder marked NSFW"** (use the wording the code's reasons map to; the "rule" reason is gone after #34, and the **NSFW folder** from #34 is a new reason).
- The same text as a **tooltip**, and available to screen-reader labels.
- The right-click menu shows the reason and offers the right action: **"Remove from NSFW"** for an item marked directly, **"Not NSFW" (override)** for an inherited tag, and nothing destructive for items that come from the NSFW folder (a note: "This file is in your NSFW folder").
- Works in dark, light and high-contrast themes and at large text sizes without clipping.
- Reasons are shown **only in the NSFW portal**, never anywhere visible in the main portals.

**Files:** `include/nsfw.h` (reason names), `src/portal_nsfw.c`, `src/ui.c` if a helper is needed, tests.

**Tests:** each reason maps to the right text; a "Not NSFW" override on an inherited item works from the menu; items from the NSFW folder offer no "Remove from NSFW"; the text never appears outside the NSFW portal.

## 3. #33: standardize the spacing between tabs

**Problem and goal:** see issue #33. Spacing values are scattered literals in `src/chrome.c` (8 dp between tabs, 52 dp or 46 dp tab widths, 36 dp after the logo, and so on).

**Fix:**
1. Define **named constants once** (for example `TAB_GAP`, `TAB_PAD_X`, `TAB_ICON_LABEL_GAP`, `TOPBAR_EDGE_MARGIN`, `LOGO_TO_TABS_GAP`), with the current look as the baseline so the first change is a **refactor with no visible difference**.
2. Replace every literal in the tab layout code; compute widths for labelled and icon-only tabs with the same helper so **gaps are equal** whatever the labels and whether a tab shows its label.
3. Same **height and minimum width** for every tab, so focus rings and hit targets line up.
4. Values stay in `dp`, so UI scale and text scale behave as before; nothing overlaps at large text sizes.
5. Review headless screenshots in dark, light and high contrast, narrow and wide; adjust the constants once; document them in the README's "Interface design" section.

The layout calculation goes in a small testable function. The tab list may later become data-driven (#27); do not build that here, but keep the layout code ready for it.

**Tests:** for 3, 5, 8 and 10 tabs and a range of widths and text scales, gaps between neighbours are equal, no tab overlaps another or the logo, everything stays inside the bar; labelled and icon-only tabs have the same height and gap; screenshots show full focus rings.

## Deviations (what was built differently, and why)
- **#34, Music and Audiobooks by kind:** the NSFW folder's videos show in the NSFW **Video** tab as well as in **Folders**, but its music and audiobooks are reached through **Folders** only. The Music and Audiobooks screens read one fixed library root each (`ROOT_MUSIC`, `ROOT_BOOKS`) in about a hundred places, so mixing in a second root would be a rewrite, not a patch. Nothing is unreachable. Filed as a follow-up issue.
