# THC 0.3.0: build spec

**Status:** ready to build. **0.2.0 has shipped** (queue, search, listening history, media keys, always-on-top, `thc-inspect`); the current version is 0.2.0. There is no 0.3.0: the fixes planned for it are part of this release. 0.3.0 is a minor release (big new features): the headline is a **separate NSFW portal** where users can mark files as NSFW (#13), alongside a Screenshots tab, settings back up and restore, a set of bug fixes, and a performance baseline.

## How to work on this (read first)
- Work on `dev`; never push to `main`. Commit and push after each slice (see "Build order").
- **Deliver 0.3.0 efficiently.** Build what this file says.
- **If you find a bug, a missing piece, an idea, or anything out of scope: file a new GitHub issue and move on.** Do not stop to fix it, and do not widen a slice. Only fix it now if it blocks the slice you are on, and say so in the commit.
- Each fix gets a test that fails before the fix and passes after.
- Keep `README.md`, `CHANGELOG.md` and this file true as you go. If you deviate from this spec, write the deviation here and say why.
- The hard rules in `AGENTS.md` still apply (no network, never write to media files, C only, three operating systems, history compatibility).

## Rules for every change
- Private and local: no network calls, no telemetry, no accounts.
- Never write to, move, or rename media files.
- Works on Windows, Linux (Wayland and X11) and macOS.

- Logic that does not need SDL goes in `thc_core` and is tested there.
- Confirmation windows are real modal dialogs.
- Anything marked NSFW must never leak into the main portals, the system, caches or logs (section 6).

## 1. #24: history must not re-key another file's entry

**Problem:** `find_moved()` in `src/history.c` re-keys a row with the same size and a different path when exactly one such row exists and the duration is unknown. If the old file still exists, saving the new file steals the old file's row.

**Fix:**
- A row counts as "moved" only if its **old path no longer exists in the library**.
- History cannot check that itself, so add `history_set_exists_check(History *h, bool (*exists)(void *ud, const char *rel_path), void *ud)`. The app passes a check that looks the relative path up in **every** library root (video, music, audiobooks, sections).
- **Safe default:** with no check set, or when the check cannot decide, **do not re-key**. A moved file then starts a fresh entry instead of a wrong one.
- `find_moved()` has **three call sites** in `src/history.c`: the lookup in `history_get()`, `history_save()`, and `history_set_watched()`. All three must follow the rule, **including plain lookups**: merely *reading* a file's history must never re-key another file's row.
- No schema change (see the History compatibility rule: nothing to migrate).

**Files:** `include/history.h`, `src/history.c`, `src/main.c` (install the check after each scan; keep it valid while the library is being replaced), `tests/test_history.c`, `tests/test_history_compat.c`.

**Tests:**
- Two files with the same size, both played: both keep their own rows (the 0.2.0 album case).
- A real move (old path gone from the library) keeps its history.
- A rename when the old path still exists elsewhere does not steal the row.
- No check installed: nothing is re-keyed.
- A plain `history_get()` of a new file (no save) does not move anyone's row.
- Existing compat tests still pass.

## 2. #20: album order with untagged files

**Problem:** `music_tracks()` (now in `src/player.c`, used by the album track list in `src/portal_music.c` and by the queue) sorts by disc and track only if **every** file has a track number. One untagged or corrupt file puts the whole album in file-name order, and the shown numbers (from tags) no longer match the order.

**Fix:**
- Tagged tracks sort by **disc, then track**. Files **without** a track number follow, in file-name order. All untagged: file-name order (unchanged).
- Move the ordering into `thc_core` as a function over an array of `TagInfo *` (some may be NULL) that returns the sort order, so it can be tested without SDL. `music_tracks()` calls it.
- **One order everywhere:** the album track list, the playback queue, and "Play" all use it.
- **Displayed numbers:** tagged tracks show their tag number; untagged tracks show "–" instead of a made-up number, so the numbers never disagree with the order.

**Files:** `include/tags.h`, `src/tags.c`, `src/player.c` (`music_tracks`), `src/portal_music.c`, `tests/test_tags.c`, `tests/test_queue.c` (queued albums use the same order).

**Tests:** mixed tagged and untagged (tagged first by track, then untagged by name); all untagged (file-name order); duplicate track numbers (stable); multi-disc; NULL tag entries; the issue's exact folder (tracks 3, 2, 1, 4 plus untagged and corrupt files gives 1, 2, 3, 4, then the rest).

## 3. #22: thumbnail keys must not collide

**Problem:** `thumb_key()` hashes only size and mtime, so batch-copied files share one thumbnail.

**Fix:**
- Key = hash of **size + mtime + the first 4 KB + the last 4 KB** of the file. Renames and moves still keep the thumbnail; different files no longer collide.
- **Read the file once per session, not every frame.** Compute the key when a file is first asked for and remember it (by path) for the session. Reading is read-only.
- Old cache entries just regenerate; the existing 500 MB prune clears the old ones.
- Unreadable files: fall back to the old key, no crash.
- Today `thumb_get()` in `src/thumbs.c` calls `thumb_key()` on every call (every frame, for every visible card), so the memo is required, not optional.

**Files:** `include/thumbs.h`, `src/thumbkey.c`, `src/thumbs.c`, `tests/test_thumbs.c`.

**Tests:** same size and mtime but different content gives different keys; same content renamed or moved gives the same key; files shorter than 8 KB; unreadable file; the key is computed once per file per session (count reads); media file unchanged.

## 4. Settings across releases, and back up / restore (new issue)

**Goal:** a user's settings and MPV setup survive upgrades, downgrades and switching package types, and can be backed up and moved to another machine.

### Settings compatibility (like history)
- `settings.ini` lives in THC's data folder, which upgrades never touch. Missing keys already fall back to defaults and unknown keys are ignored.
- **Gap:** an older THC saves only the keys it knows, so a downgrade silently drops newer settings. **Fix:** when loading, keep every key and value in the file that THC does not recognize, and write them back unchanged on save. Known keys are rewritten as usual.
- **Rule going forward** (also added to `AGENTS.md`): never rename or remove a settings key; to change one, add a new key and migrate the old value on load (as `remember_history` was migrated). A newer value an older THC does not understand must not be damaged.

### Same data folder for every package
- The Snap keeps its data in a different folder from the .deb, AppImage and tarball, so switching package type looks like a fresh install. Check what folder each package uses, document it in the README ("Where THC keeps its files"), and where possible make them agree. If a package cannot share the folder, say so in the README and rely on back up / restore (below).
- Uninstalling or upgrading on every OS (Windows installer, macOS app, Linux packages) must **leave the data folder alone**. Check each package script in `packaging/` and `snap/`.

### Back up and restore (Settings → Privacy, or a Backup section)
- **Back up** copies to a folder the user chooses: `settings.ini` and the whole `mpv/` folder (`mpv.conf`, `input.conf`, `script-opts/`, `scripts/`, `shaders/`), with checkboxes to also include **watch and listening history** (`history.db`, copied safely with SQLite's backup function) and **screenshots** (off by default). It never includes media files, thumbnails or other caches. The backup is a plain folder, so the user can zip or sync it however they like, and no new dependency is needed.
- **Restore** reads such a folder, shows what it contains and its THC version, and asks in a **confirmation window**. Before changing anything it saves the current files into a `pre-restore` folder in the data folder. Files are staged and applied **on the next start**, so the history database is never swapped while it is open.
- A backup from a newer THC restores what this THC understands and says what it skipped. A folder with no `settings.ini` is refused with a clear message.
- Writes only inside the folder the user picked (backup) and THC's data folder (restore). Restore uses only the known file names, never paths taken from the backup (no path traversal).
- README: tell users to back up `mpv.conf` and the `mpv/` folder (or use this button) before reinstalling, and where the data folder is on each OS.

| Key | Type | Default |
| --- | --- | --- |
| none | back up / restore are actions, not settings | |

### Files
`src/settings.c`, `include/settings.h` (preserve unknown keys), `src/screen_settings.c` (the Backup section and dialogs), a new small core module for backup and restore logic (testable without SDL), `src/history.c` (safe copy), `packaging/`, `snap/snapcraft.yaml`, `AGENTS.md` (settings compatibility rule), `README.md`.

### Tests
- Unknown keys survive a load and save, in order, with their values; known keys still update.
- A settings file from a "newer" version (extra keys) round-trips without loss.
- `remember_history`-style migration still works.
- Back up writes the expected files and nothing else; history is included only when chosen and the copy opens as a valid database.
- Restore: stages and applies on next start; the pre-restore copy exists; refuses a folder without `settings.ini`; ignores unexpected file names and path tricks in a crafted backup; a newer-version backup restores what it can.
- Media folders are never touched.

## 5. #25: MPV screenshots go to THC's folder and show up in THC

### Behavior
- Pressing MPV's screenshot key (`s`) saves to **`<THC data folder>/screenshots/`**, never to a media folder or the working directory.
- THC sets MPV's `screenshot-directory` after startup (as a property, since `mpv.conf` overrides earlier options), like its other controlled options.
- A new **top-level Screenshots tab** in the top bar, next to Video, Music and Audiobooks, with its own hotkey (remappable). It shows a grid of the saved images, newest first, with the video title and time from the file name. Selecting one opens it larger.
- Adding a tab touches the screen list and the top bar (`Screen` enum, `src/chrome.c` tabs, `last_portal` saving and loading, the portal-switch hotkeys) and must not break the existing three tabs; keep keyboard navigation and focus order working.
- Per image: open in the file manager, copy path, **delete** (confirmation window).
- Empty state explains where screenshots go and how to take one.
- Screenshots are what you watched, so they stay local and appear in `thc-inspect`'s file list.

### Settings
| Key | Type | Default |
| --- | --- | --- |
| `screenshot_dir` | path | empty = `<data>/screenshots` |
| `screenshot_format` | png / jpg / webp | **png** (default) |
| `screenshot_tab_hotkey` | key | remappable |
| `screenshot_template` | MPV template | `%{media-title}-%P` |

- THC controls these three MPV options (`screenshot-directory`, `screenshot-format`, `screenshot-template`). Add them to the **THC-controlled list in `src/mpvconf.c`** (next to `ontop`), so the config check marks them as ignored in `mpv.conf`, and update `tests/test_mpvconf.c`.
- The folder is created if missing; if it cannot be written, THC says so instead of failing silently.

### Files
`src/video.c`, `src/main.c`, `src/chrome.c` and `src/app.h` (the tab and screen), a new `src/portal_screenshots.c` (the gallery), `src/art.c` (images load through the existing cache; very large screenshots are subject to the same limits as any image until #21 is fixed, so keep MPV's screenshots at their normal size), `src/screen_settings.c`, `src/settings.c` and `tests/test_settings.c` (round trip of the three keys), `src/mpvconf.c`, `tools/inspect/` and `tests/test_inspect.c` (list the screenshots folder with the other files THC writes), `README.md` (the "Where THC keeps its files" section).

### Tests
MPV is started with the right directory, format and template (also when `mpv.conf` sets different values); the folder is created; the Screenshots tab is reachable by mouse, keyboard and hotkey and the other tabs still work; the gallery lists files newest first and ignores non-images; delete removes only files inside the screenshots folder (path check); a custom folder works; nothing is written into the media folder.

## 6. NSFW portal and marking (#13) — the headline feature

**Goal:** a **separate NSFW portal**, and a way to **mark any file, show, album or folder as NSFW**. Marked items leave the normal portals and live only in the NSFW portal. It is optional, off by default, local only, and presentation-only: **tags live in THC's database and nothing on disk is touched.** The design follows issue #13; where that issue left a choice open, the decision is written here.

### 6.1 What the user sees
- **Off by default.** Until the user turns on **Settings → Privacy → Enable NSFW portal**, there is no NSFW tab, no "Mark as NSFW" action and no change anywhere.
- **Easy to hide (see 6.1a).** The tab can be hidden in one action and shown again just as fast.
- **A new top-level tab "NSFW"** in the top bar (after Audiobooks; Screenshots is the other new tab). It always shows a text label as well as its icon.
- **Icon: a beer bottle with a label reading "XXX".** Add a vector icon (`ICON_BEER`, drawn like the other icons in `src/ui.c`) used on the tab, the lock screen and the empty state. At small sizes the label is drawn as three small crosses. It must read clearly in dark, light and high-contrast themes.
- **The portal has its own look** (a distinct accent and mood, like Cinema, Vinyl and Library; document the choice in the README) and three sub-tabs: **Video, Music, Audiobooks**. Each reuses the existing views (rows, shows, albums, books) but shows **only NSFW items**. Nothing else changes about how content is browsed or played.
### 6.1a Hiding the portal quickly
**Hidden is not the same as off.** *Off* removes the feature. *Hidden* only takes the NSFW tab out of the top bar: marked items **stay out of the main portals**, their tags and settings are kept, and nothing is deleted.

- **Hide or show with one action, three ways:**
  1. a **remappable hotkey** (default **`Ctrl+Shift+H`**) that toggles the tab at once;
  2. **right-click the NSFW tab, then "Hide NSFW tab"**;
  3. a **Hide NSFW tab** switch in Settings → Privacy.
- **Hiding takes effect immediately and completely:** the tab disappears, THC leaves the NSFW portal for the last normal portal, the portal **locks** (if a PIN is set), and no NSFW title or picture remains on screen. A short toast says "NSFW tab hidden" without naming anything.
- **If an NSFW item is playing** when the tab is hidden, playback **stops** (setting `nsfw_hide_stops_playback`, on by default); with it off, playback continues but the item stays masked.
- **Showing it again** uses the same hotkey or the Settings switch. If a PIN is set, the tab appears but the portal still asks for it.
- **The hidden state is remembered** across restarts (`nsfw_tab = hidden`), so THC can start with it hidden.
- While the tab is hidden, the "Mark as NSFW" action and the N key still work (so a user can keep marking without revealing the portal), but they only ever show a plain confirmation toast.
- The hotkey works from **every screen**, including during playback in THC's own window; it is not required to work inside the MPV window (the panic key covers that).
- Hiding and showing can be **spammed**: the final state must always match the last press.

- **Marking:** on any card or row, a context-menu action **"Mark as NSFW" / "Remove from NSFW"**, plus a remappable key (default **N**) and a bulk action on a show page ("Mark season as NSFW"). A tag can be put on: a file, an episode, a movie, a season, a show, an album, an artist, an audiobook, or **any folder**. A folder tag applies to everything inside it, **including files added later**.
- Items **disappear from the normal portals immediately** (a toast confirms, with Undo).
- In the NSFW portal each item can show **why** it is NSFW (the item itself, a parent folder, a library section or folder, or a rule) so nothing is a mystery; an inherited tag is removed by untagging the parent, or overridden by an explicit "Not NSFW" on the item.
- **Whole library folders or sections:** in **Settings → Library**, "Treat this folder as NSFW" on any library root or section.
- **Rules (optional, off by default):** a list of folder names or simple patterns (for example `NSFW`, `*xxx*`, case-insensitive) that count as NSFW. Local only. Rules never override an explicit "Not NSFW".
- **Tag list import and export** as a plain text file (paths relative to the library). Because the list reveals what is tagged, **export and view require the lock to be open** (6.4).

### 6.2 Defaults (most private choices)
| Decision | Default |
| --- | --- |
| Handling | **Separate portal** only (hide from main portals; no blur or "warn first" modes in 0.3.0) |
| History for NSFW items | **Not recorded** (no resume, no plays, no "recently played"); a setting turns it on |
| Thumbnails and screenshots of NSFW items | Stored apart, **cleared when THC exits** |
| Tab visibility | Visible once enabled; **one-action hide and show** (6.1a); not present at all while the portal is off |
| Lock | Off until the user sets a PIN |
| Titles shown to the system | Never (see 6.5) |

### 6.3 Settings
| Key | Type | Default |
| --- | --- | --- |
| `nsfw_enabled` | bool | false |
| `nsfw_tab` | visible / hidden | visible |
| `nsfw_hide_stops_playback` | bool | true |
| `nsfw_record_history` | bool | false |
| `nsfw_clear_thumbs_on_exit` | bool | true |
| `nsfw_confirm_before_open` | bool | false |
| `nsfw_mask_titles` | bool (window title, OSD, queue, now playing) | true |
| `nsfw_rules_enabled` | bool | false |
| `nsfw_rules` | list of names/patterns | empty |
| `nsfw_pin_salt`, `nsfw_pin_hash` | text (never shown) | empty |
| `nsfw_relock_minutes` | int, 0 = never | 10 |
| hotkeys | mark (**N**), panic (**`Ctrl+Shift+X`**), hide/show tab (**`Ctrl+Shift+H`**) | remappable |

Add every key to `tests/test_settings.c` and follow the settings compatibility rule (unknown keys preserved; never rename).

### 6.4 Lock (optional PIN)
- Optional **PIN or passphrase** to open the NSFW portal and to change NSFW settings. **Be honest in the README: this is a courtesy lock, not security.** Media files and THC's data files are not encrypted.
- Stored as a **salted, iterated hash** (PBKDF2-HMAC-SHA256 with a few tens of thousands of iterations, using a small **public-domain SHA-256**; no GPL code; record the choice in the README). The PIN is never stored or logged in plain text.
- **Auto-relock:** after `nsfw_relock_minutes` of inactivity, on quit, on **panic**, and when the screen locks (where the OS tells us). A locked portal shows only the bottle icon and a PIN field, with no titles or art.
- **Forgot the PIN:** "Reset NSFW lock" clears the PIN after a typed confirmation, and says plainly that this lock is not security. Nothing is deleted.
- Fully keyboard accessible, scalable text, and screen-reader-friendly labels.

### 6.5 Panic key and leak protection
Every place that can show a title or picture must follow the tag. Each needs a test.

- **Panic key** (default `Ctrl+Shift+X`, remappable): immediately **stops NSFW playback, closes the MPV window, silences audio, leaves the NSFW portal for the last normal portal, locks it, and removes NSFW items from every queue and backlog.** It must also work **inside the MPV window**: THC binds the key in MPV with `keybind <key> script-message thc-panic` and handles MPV's **client-message event** (event id 16, add it to `mpv_dyn.h`); the in-THC hotkey covers the rest. Pressing it repeatedly must be safe, and the final state must match the last press.
- **Main portals:** Continue watching, Up next, Recently added, Recently played, Most played, counts, section rows, **music search** (the index excludes NSFW), the queue suggestions and the "Add to queue" paths all exclude NSFW items. Use **one shared function** (in `thc_core`, for example `nsfw_hidden(root, relpath, kind)`) so no view can forget it.
- **History and plays:** not recorded for NSFW items unless `nsfw_record_history` is on; even then they are excluded from the main portals' lists.
- **Window title, OSD and system media controls:** the MPV window title is the fixed text "THC" for NSFW items (`nsfw_mask_titles`), media keys and now-playing always share "Playing" only, and the OS "recent files" list never gets NSFW paths.
- **Thumbnails and screenshots:** NSFW thumbnails go in `thumbs/nsfw/` and are removed on exit (when the setting is on); **screenshots taken while an NSFW item plays go to `screenshots/nsfw/`** (set `screenshot-directory` per playback) and show only in the NSFW portal. MPV scripts the user installs are out of THC's control; **document that in the README**.
- **Logs and errors:** never print NSFW file names, paths or titles (use "a hidden item").
- **`thc-inspect`** reports the number of NSFW tags and whether `thumbs/nsfw/` is empty, and prints names only with `--show-titles` and never for NSFW items.
- **Back up / restore:** the tag list is in `history.db`, so it is included only with the "include history" box, and the backup screen says so.

### 6.6 Data model
- Schema **version 3** of `history.db`: one numbered migration (follow the **History compatibility** rule: only add tables and indexes, bump `HISTORY_SCHEMA_VERSION`, extend `tests/test_history_compat.c`).
- New table `nsfw_tags`: `id`, `root` (video / music / audiobooks / section), `rel_path`, `scope` (file or folder), `size` (file tags only), `state` (1 = NSFW, 0 = explicitly not NSFW), `created`.
- **File tags** are keyed like history (relative path + size) and follow a moved file the same way (using the #24 exists check). **Folder tags** are keyed by relative path; **inheritance is computed when read**, so moving a file changes its effective tag with no extra writes.
- **Conflict rules:** an explicit "Not NSFW" beats an inherited tag and a rule; a file inside two NSFW folders is just NSFW; an NSFW season in a non-NSFW show hides that season in the normal show page and the show still appears with its other seasons.
- A very large library must stay fast: the tag lookup is cached per scan and per queue build, not a database query per card per frame.

### 6.7 Files
New: `include/nsfw.h`, `src/nsfw.c` (core: tags, inheritance, rules, PIN hash, no SDL), `src/portal_nsfw.c` (the portal and lock screen), a small public-domain SHA-256 in `third_party/` (with its license). Changed: `include/history.h` / `src/history.c` (migration, tag table), `src/app.h` (screen and root plumbing), `src/chrome.c` (the tab; the top bar currently assumes three tabs), `src/ui.c` and `include/ui.h` (`ICON_BEER`, a `PORTAL_NSFW` theme), `src/library.c` and `src/portal_video.c` / `portal_music.c` / `portal_books.c` (filter), `src/search.c` and the index build, `src/player.c` (queue and panic), `src/video.c` and `src/main.c` (window title, per-playback screenshot folder, client message, panic), `src/mediakeys*.c` (titles), `src/thumbs.c` (NSFW cache), `src/mpv_dyn.h`, `src/settings.c`, `include/settings.h`, `src/screen_settings.c`, `tools/inspect/`, `CMakeLists.txt`, `README.md`.

### 6.8 Tests
- **Database:** create, delete, folder inheritance, explicit untag override, conflicts, migration v2→v3 (compat tests), key stability after a rename or move (with and without the old path existing).
- **Filtering:** each main view excludes NSFW items (library build, counts, Continue watching, Up next, recently added and played, search, queue add, queue suggestions) and the NSFW portal shows only them; a file added later to a tagged folder is hidden.
- **Rules:** names and patterns, nesting, and "Not NSFW" overriding a rule.
- **Lock:** PIN set, check and wrong PIN; the hash is salted and iterated and the PIN never appears in `settings.ini` or logs; relock timers (fake clock); reset.
- **Leaks:** window title masked; media keys share "Playing" only; history, plays and backlog not recorded; thumbnails and screenshots in the NSFW folders and removed on exit; no NSFW names in logs; `thc-inspect` output.
- **Panic:** stops and closes during library browsing, music, audiobook and video playback, including from inside the MPV window; clears NSFW queue items; works when pressed repeatedly (spam test, final state equals the last press).
- **Off by default:** with the portal disabled nothing changes and no NSFW action appears.
- **Hide and show:** the hotkey, the tab's right-click menu and the Settings switch all hide and show the tab; hiding leaves the portal, locks it, stops or masks playback per the setting, and keeps tags and the main portals' filtering; the state survives a restart; spamming the hotkey ends in the state of the last press; hidden is distinct from off.
- Media files are never modified; no network traffic.
- UI smoke (headless screenshot): NSFW tab, bottle icon in dark, light and high contrast, lock screen, marking toast.

### 6.9 Out of scope for 0.3.0 (file as issues)
Blur or cover mode and "warn first" mode for items in the main portals, a "boss key" that blurs the whole app, NSFW search inside the NSFW portal, tag-by-content classification (never: no classifiers, no network).

## 7. #12: performance baseline

**Goal:** know how fast and how big THC is before 0.4, without optimizing yet.

- Add `tools/perf/`: a script that builds a **synthetic library** (for example 1,000 / 10,000 / 50,000 files, with tags and a few covers) in a temp folder, and a way to run THC headless against it.
- Record, per size: **scan time, tag-read time, peak memory, time to first frame, frame time while scrolling, search latency per keystroke (once 0.2.0 search exists), queue operations with large queues.**
- A small headless hook in THC (for example an environment variable that prints timings and exits) is allowed for this; keep it out of normal use and document it.
- Write results and **targets** to `docs/performance.md`.
- **Do not optimize in this release** except trivial one-line wins. For anything slow or large, **file an issue** with the numbers.
- An optional manual or nightly CI job runs the 1,000-file case.

**Done when:** `docs/performance.md` has a table of measured numbers on at least Linux, the script is committed and documented, and any problems found are filed as issues.
